## §16.4 Phase Plan (Dependency-Ordered)

### Phase 1 — Foundation (Weeks 1–2)
**Goal:** Repository, local dev, CI, core architecture skeleton.

Deliverables:
- Monorepo setup (`apps/web`, `apps/api`, `apps/collab`, `apps/worker`, `packages/shared`)
- Docker Compose (Postgres + Redis + MailHog)
- Prisma schema baseline + migrations pipeline
- Global API standards enforced (response envelope, error format, requestId)
- Basic logging + health endpoints
- CI pipeline: lint/typecheck/unit tests/build

Exit criteria:
- New contributor can run the project locally end-to-end
- CI is green on main branch
- API returns “hello” endpoint with requestId

---

### Phase 2 — Identity & Access (Weeks 2–4)
**Goal:** Auth working + RBAC foundations.

Deliverables:
- Local auth:
  - register, verify email, login, refresh, logout
  - forgot/reset password
- Google OAuth login
- Users “me” endpoint + profile update basics
- Global admin guard + admin route gating
- Base RBAC guards for workspace-scoped routes (membership required)

Critical tests:
- Auth flows E2E (FL-001, FL-002)
- Token rotation correctness
- Deactivated user blocked
- Basic security audit logging for auth events

Exit criteria:
- A user can create an account, login, refresh session, logout
- Admin-only endpoints are truly admin-only

---

### Phase 3 — Workspaces & Membership (Weeks 4–6)
**Goal:** Workspaces become usable containers with roles.

Deliverables:
- Workspace CRUD (create/read/update/archive/delete)
- Workspace types (professional/academic/general) stored + defaults applied
- Membership list
- Invitation flow (invite → accept → join)
- Role changes + enforcement
- Workspace switcher + navigation context

Critical tests:
- Invite flow E2E (FL-004)
- Workspace isolation tests (cannot access other workspace by guessing ids)

Exit criteria:
- Two users can join the same workspace and see it
- Role differences are enforced (Viewer cannot create/edit)

---

### Phase 4 — Templates (Weeks 6–7)
**Goal:** Workspace creation becomes structured and repeatable.

Deliverables:
- System templates stored and listable
- Workspace creation wizard uses templates
- Workspace template application engine creates:
  - folders
  - starter documents
  - task columns
  - workspace settings + role labels mapping

Exit criteria:
- Creating a workspace from template generates expected structure every time
- Template application is transactional (no partial workspaces)

---

### Phase 5 — Documents: Metadata + Hierarchy (Weeks 7–8)
**Goal:** Document tree works (even before realtime collaboration).

Deliverables:
- Folder CRUD
- Document metadata CRUD (title, folder, ordering)
- Document tree endpoint + tree UI
- Document list page + sidebar tree
- Lock/unlock document (metadata-level)
- Basic export placeholders (queue scaffolding)

Exit criteria:
- Users can create folders/docs and reorder them
- Locks reflect in UI and block editing (once editor exists)

---

### Phase 6 — Realtime Collaboration (Weeks 8–10) **(Critical Path)**
**Goal:** Real-time editor works reliably.

Deliverables:
- Tiptap editor integrated in web app
- Hocuspocus server running with:
  - JWT auth
  - workspace membership validation
  - document permission enforcement (read-only vs editable)
  - persistence hooks to Postgres (`documents.content_yjs`)
- Presence indicators (avatars)
- Cursors (P1 if feasible in v1)
- Offline/reconnect UX banners

Exit criteria:
- Two users can open same doc and see edits live (FL-005)
- Content persists across refresh
- Viewer cannot edit; server rejects edits

---

### Phase 7 — Comments & Mentions (Weeks 10–11)
**Goal:** Discussions are possible around docs and tasks.

Deliverables:
- Comment threads targeting document/task
- Thread replies
- Resolve/reopen thread (Manager+)
- Mentions parsing + notification triggers
- Realtime comment updates via Socket.IO

Exit criteria:
- Comments appear live to other users
- Mentions generate notifications
- Permissions enforced

---

### Phase 8 — Tasks (Weeks 11–13)
**Goal:** Teams can manage work with Kanban + basic list view.

Deliverables:
- Task CRUD + state machine enforcement
- Kanban board UI with drag/drop
- Task detail panel
- Assignment constraints + notifications
- Task list view (P1)
- Due date reminders (worker job)

Exit criteria:
- Two users see task changes live (FL-006)
- Assigned user receives notification
- Invalid transitions blocked

---

### Phase 9 — Notifications + Activity + Search (Weeks 13–15)
**Goal:** Make the platform feel “alive” and navigable.

Deliverables:
- In-app notifications (bell + center) + unread count
- Email notifications baseline + preferences
- Activity feed generation from domain events
- Search:
  - documents (title + plaintext)
  - tasks (title + description)

Exit criteria:
- Notifications arrive in-app in realtime (FL-008)
- Search returns correct workspace-scoped results (FL-009)
- Activity feed shows meaningful events

---

### Phase 10 — Academic Submission Workflow (Weeks 15–16)
**Goal:** Academic mode differentiator works end-to-end.

Deliverables:
- Document submit endpoint + lock editing while submitted
- Supervisor review decision (approve/changes requested)
- Submission history records + snapshots
- Notifications for submit + review outcome

Exit criteria:
- Academic workflow passes E2E (FL-010)
- Students cannot edit submitted docs; supervisors can review

---

### Phase 11 — Admin Console + Hardening (Weeks 16–18)
**Goal:** Operate safely; improve quality.

Deliverables:
- Admin dashboard basics
- User management (deactivate/reactivate)
- Workspace management (list/view/archive/force delete)
- Audit log access
- Observability dashboards (minimal) + alerts (minimal)
- Performance and security sweep

Exit criteria:
- Admin can manage users and inspect audit logs
- No critical OWASP issues discovered in baseline scan

---
