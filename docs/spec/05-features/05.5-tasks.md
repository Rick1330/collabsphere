# §5.5 Tasks (Boards, List View, Statuses, Assignment, Due Dates, Reminders, Bulk Ops)

## §5.5.1 Overview

The Tasks capability provides structured work tracking inside a workspace. It supports:

- Kanban board (drag-and-drop)
- Task list/table view (filter/sort/paginate)
- Assignment and ownership (reporter vs assignee)
- Priorities, due dates, labels
- Task comments (discussion thread) and mentions (see §4.8)
- Notifications and reminders (see §4.9)
- Activity logging for meaningful task events (see §5.9 later)

**Priority:**  
- P0: Task CRUD + Kanban board + assignment + status transitions  
- P1: Task list view + filters + reminders (due soon/overdue)  
- P2: Labels + bulk actions + advanced filters  
- P3: Dependencies + calendar/timeline views

## §5.5.3 Task Concept Model

### §5.5.3.1 Reporter vs Assignee
- **Reporter**: user who created the task (immutable in v1)
- **Assignee**: user responsible for completing the task (nullable)

### §5.5.3.2 Task Column vs Task Status
- A **TaskStatus** is a canonical state (`todo`, `in_progress`, etc.)
- A **TaskColumn** is a board UI column that maps to a TaskStatus (and can be renamed)

**Example:**
- Column name: “Testing”
- Column status: `in_review`

This allows different naming without changing the underlying state machine.

## §5.5.4 Statuses & State Machine (Authoritative)

### §5.5.4.1 Canonical Status Enum (v1)
- `backlog` (optional; enabled by template)
- `todo`
- `in_progress`
- `in_review`
- `done`

Optional (P2/P3):
- `cancelled`
- `archived` (system-only, used for retention)

### §5.5.4.2 Allowed Transitions (v1)

| From | To | Allowed Actor | Notes |
|------|----|---------------|------|
| backlog | todo | Member+ | |
| todo | in_progress | Assignee OR Manager+ | If unassigned, Member can move only if they self-assign simultaneously (policy option) |
| in_progress | in_review | Assignee OR Manager+ | |
| in_review | in_progress | Manager+ | “Changes requested” / rework |
| in_review | done | Manager+ | Default for quality control |
| done | in_progress | Manager+ | Reopen |

Rules:
- If a transition is attempted and invalid, return `400 INVALID_TRANSITION`.
- UI must prevent invalid transitions via disabled drop targets and clear messaging.

## §5.5.5 Kanban Board (P0)

### Route
- `/w/:workspaceId/tasks`

### Board Requirements
- Columns displayed left-to-right in `task_columns.position` order
- Column header shows:
  - name
  - count
  - “+ Add Task” (Member+)
- Cards show:
  - title
  - priority indicator
  - assignee avatar or “Unassigned”
  - due date badge (overdue styling)
  - comment count (if >0)
  - up to 2 labels (+N)

### Drag & Drop Requirements
- Optimistic UI update
- On drop:
  - call status/position endpoint
  - if failure: snap back and show toast with reason
- Accessibility:
  - keyboard move alternative (see §3.6)
  - ARIA announcements on move success

### Ordering within columns
- Maintain manual ordering using `tasks.position` (decimal)
- When dropped:
  - compute new position between adjacent tasks (fractional)
  - periodic rebalance (P3)

## §5.5.7 Task Fields & Validation (Authoritative)

| Field | Validation Rule | Error Code |
|------|------------------|-----------|
| title | required, 1–200 chars | `VALIDATION_ERROR` |
| description | max 10,000 chars | `VALIDATION_ERROR` |
| assigneeId | must be workspace member or null | `INVALID_ASSIGNEE` |
| dueDate | must be today or future (recommended) | `INVALID_DATE` |
| priority | must be one of enum | `VALIDATION_ERROR` |
| labels | max 10 labels; each 1–30 chars; `[a-zA-Z0-9-]` only | `INVALID_LABEL` |

## §5.5.9 Due Dates & Reminders (P1)

### Due Date Rules
- Date-only (no time) in v1
- Overdue definition:
  - overdue if `dueDate < today` AND status not in `{done, cancelled}`
- “Due soon”:
  - due within next 24 hours (or next day boundary)

### Reminder Events
- System job runs every hour (or daily at 9am + 5pm):
  - finds tasks due soon/overdue
  - sends notifications based on preferences (§4.9)

---

## §5.5.10 Labels (P2)

Labels help group tasks (e.g., `frontend`, `backend`, `urgent`).

v1 approach options:
1) Store labels as `text[]` on tasks (fastest for v1)  
2) Normalize into `labels` table + join table (better for analytics, suggestions)

**Recommendation:**  
- v1: `text[]` on tasks + workspace-level label suggestions computed from existing labels  
- v1.1+: add normalized labels if needed

## §5.5.11 Bulk Operations (P2)

Available to Manager+ only.

Bulk actions:
- Change status
- Assign assignee
- Change priority
- Add/remove labels
- Delete tasks

Bulk rules:
- Validate each task:
  - if any invalid transitions, skip those and return partial success report
- UI shows summary:
  - “14 updated, 2 skipped (invalid transition)”

## §5.5.14 API Contracts (Authoritative)

Base: `/api/v1/workspaces/:workspaceId/tasks`

### 1) Create Task
`POST /api/v1/workspaces/:workspaceId/tasks`

(As defined in §4.7; included here as authoritative.)

---

### 2) List Tasks (List View)
`GET /api/v1/workspaces/:workspaceId/tasks?view=list`

Query params:
- `page`, `pageSize`
- `status=todo,in_progress`
- `assigneeId=<uuid>|unassigned`
- `priority=high,urgent`
- `dueBefore=YYYY-MM-DD`
- `dueAfter=YYYY-MM-DD`
- `search=...`
- `sortBy=createdAt|updatedAt|dueDate|priority|title`
- `sortOrder=asc|desc`

---

### 3) List Tasks (Board View)
`GET /api/v1/workspaces/:workspaceId/tasks?view=board`

Response groups tasks by status:
```json
{
  "data": {
    "columns": [
      {
        "status": "todo",
        "name": "To Do",
        "tasks": [ { "id": "uuid", "title": "..." } ],
        "totalCount": 12,
        "hasMore": false
      }
    ]
  }
}
```

Notes:
- Optionally support lazy loading per column (`?status=todo&page=2`) if columns can be large.

---

### 4) Get Task Detail
`GET /api/v1/workspaces/:workspaceId/tasks/:taskId`

Response:
```json
{
  "data": {
    "task": {
      "id": "uuid",
      "title": "Implement login page",
      "description": "…",
      "status": "in_progress",
      "priority": "high",
      "assignee": { "id": "uuid", "fullName": "Jane Doe" },
      "reporter": { "id": "uuid", "fullName": "Alice" },
      "dueDate": "2025-08-01",
      "labels": ["frontend", "auth"],
      "createdAt": "2025-07-17T12:00:00Z",
      "updatedAt": "2025-07-17T12:10:00Z"
    }
  }
}
```

Errors:
- `404 TASK_NOT_FOUND`
- `403 NOT_WORKSPACE_MEMBER`

---

### 5) Update Task Fields (title/desc/priority/dueDate)
`PATCH /api/v1/workspaces/:workspaceId/tasks/:taskId`

Request:
```json
{
  "title": "Implement login page (UI)",
  "priority": "urgent",
  "dueDate": "2025-07-25"
}
```

---

### 6) Assign Task
`PATCH /api/v1/workspaces/:workspaceId/tasks/:taskId/assign`

Request:
```json
{ "assigneeId": "uuid-or-null" }
```

Errors:
- `403 FORBIDDEN`
- `400 INVALID_ASSIGNEE`

---

### 7) Change Status (and Position)
`PATCH /api/v1/workspaces/:workspaceId/tasks/:taskId/status`

Request:
```json
{
  "toStatus": "in_review",
  "positionAfter": 3.5
}
```

Errors:
- `400 INVALID_TRANSITION`
- `403 FORBIDDEN`

---

### 8) Delete Task (Soft Delete)
`DELETE /api/v1/workspaces/:workspaceId/tasks/:taskId`

Role:
- Manager+ for any
- Member only for own task

Response:
```json
{ "data": { "message": "Task deleted." } }
```

---

### 9) Bulk Update (P2)
`POST /api/v1/workspaces/:workspaceId/tasks/bulk`

Request:
```json
{
  "taskIds": ["t1","t2"],
  "operation": "assign",
  "payload": { "assigneeId": "uuid" }
}
```

Response includes per-task results.

## §5.5.15 Data Model (Authoritative)

### `tasks`
- `id UUID PK`
- `workspace_id UUID FK`
- `title VARCHAR(200)`
- `description TEXT NULL` (plain text only in v1)
- `status ENUM('backlog','todo','in_progress','in_review','done')`
- `priority ENUM('low','medium','high','urgent')`
- `assignee_id UUID NULL`
- `reporter_id UUID NOT NULL`
- `due_date DATE NULL`
- `labels TEXT[] NOT NULL DEFAULT '{}'` (v1)
- `position DECIMAL NOT NULL`
- `created_at`, `updated_at`, `deleted_at`

Indexes:
- `(workspace_id, status, position)`
- `(workspace_id, assignee_id, due_date)`
- `(workspace_id, updated_at DESC)`
- Search vector index (if you include task search here; see §4.10)

### `task_columns` (P0 if columns are configurable by template)
- `id UUID PK`
- `workspace_id UUID FK`
- `name VARCHAR(50)` (display)
- `status ENUM(...)` (canonical)
- `position DECIMAL`
- `is_hidden BOOLEAN DEFAULT false` (P2)
- `created_at`, `updated_at`

> v1 minimal: create columns at workspace creation from template and treat them as read-only (no UI to edit column names). Still store `task_columns` to avoid hardcoding.

## §5.5.17 Edge Cases (Must Be Handled)

| Scenario | Expected Behavior |
|---------|-------------------|
| Member tries to move task they don’t own | Deny (403) unless Manager+. UI shows “You can only move tasks assigned to you.” (policy choice). |
| Unassigned task moved to In Progress by Member | If self-assign enabled: auto-assign to that member; else deny with message. |
| Assignee removed from workspace | Set assignee null; emit `task.unassigned_due_to_member_removal`. |
| Concurrent moves | Last-write wins; realtime updates settle clients. |
| Task due date changed to past | Reject with `INVALID_DATE` (recommended). |
| Workspace archived | Deny task create/update/delete with `WORKSPACE_ARCHIVED_READONLY`. |
| Very large board | Lazy-load per column; do not render 1000 cards at once. |
| Viewer access | Ensure all mutation endpoints are blocked; list endpoints still allowed. |
