# §5.2 Workspaces (Types, Settings, Membership, Roles)

## §5.2.1 Overview

A **Workspace** is the primary collaboration boundary in CollabSphere. All documents, tasks, files, activity, and permissions are scoped to a workspace. Workspaces support:

- Workspace creation and configuration
- Workspace type selection (Professional / Academic / General)
- Member invitation and membership management
- Workspace roles (Owner/Admin/Manager/Member/Viewer)
- Workspace switcher and navigation context
- Workspace lifecycle (active → archived → deleted)

**Priority:** P0 (launch-blocking)

---

## §5.2.2 Key Concepts

### §5.2.2.1 Workspace vs Membership

- A **Workspace** is a container for project content.
- A **WorkspaceMember** is the relationship between a user and a workspace.
- A user can belong to many workspaces and have different roles per workspace.

### §5.2.2.2 Workspace Types (Modes)

Workspace types shape:
- which templates are shown by default
- which workflows are enabled (Academic submission/review)
- how roles are labeled in the UI (cosmetic mapping)

**Types:**
- `professional`
- `academic`
- `general`

> The permission system is identical across types; types only affect defaults and feature flags.

---

## §5.2.3 Personas & Permissions

### Workspace-level roles (per §2)
- Owner
- Admin
- Manager
- Member
- Viewer

### Capabilities (summary)
- **Any authenticated user:** can create a workspace (becomes Owner)
- **Owner/Admin:** can edit workspace settings, manage members/invites, archive
- **Owner only:** can delete workspace, transfer ownership
- **Manager+:** can view analytics (if enabled), manage work processes (tasks/review)
- **Viewer:** read-only access to workspace content per rules

---

## §5.2.4 Workspace Lifecycle (State Machine)

### States (v1)
- `active`
- `archived`
- `deleted` (soft deleted)

### Transition Rules

| From | To | Who | Notes |
|------|----|-----|------|
| active | archived | Owner/Admin | Workspace becomes read-only for non-admin actions (policy below) |
| archived | active | Owner/Admin | Restores workspace to normal operation |
| active | deleted | Owner | Soft delete with grace period |
| archived | deleted | Owner | Allowed |
| deleted | — | System | Purged after retention (e.g., 90 days) |

### Archived Workspace Policy (v1)

When archived:
- **View**: allowed to all members
- **Create/Edit** documents/tasks/files: disabled for Member/Viewer/Manager
- **Admin actions**:
  - Owner/Admin can unarchive
  - Owner/Admin can still manage members (optional; recommended: allow manage members, but disallow invites unless unarchived)
- UI shows banner: “This workspace is archived (read-only).”

## §5.2.5 UI/UX Specifications (Web)

### §5.2.5.1 Workspace Switcher (Top Nav)

Requirements:
- Lists all workspaces user belongs to
- Sorted by last accessed (descending), then name
- Shows:
  - icon (emoji/icon)
  - workspace name
  - workspace type badge (optional)
- Search within switcher if user has >10 workspaces
- “Create workspace” action at bottom
- Keyboard shortcut: `Cmd+W` / `Ctrl+W`

### §5.2.5.2 Workspace List Page

Route: `/workspaces`

Shows cards (or table) with:
- icon + name
- description snippet
- role label (mapped by workspace type)
- last activity time
- quick actions:
  - open workspace
  - (Admin+) settings shortcut
  - (Owner/Admin) archive/unarchive (optional from list)

States:
- Loading skeleton
- Empty state: “You haven’t joined any workspaces yet” + Create CTA
- Error state + Retry

### §5.2.5.3 Workspace Home (Overview Dashboard)

Route: `/w/:workspaceId`

Shows summary widgets:
- My tasks (top 5)
- Recent documents (top 5)
- Recent activity (top 10)
- Submission queue (academic type, supervisor/admin only)
- Quick actions: new doc, new task, invite members (Admin+)

### §5.2.5.4 Workspace Settings

Route: `/w/:workspaceId/settings` (Admin+)

Tabs (v1):
- General
- Members (or link to /settings/members)
- Danger Zone (Owner-only actions)

General settings fields:
- name (3–60 chars)
- description (0–280 chars)
- icon (emoji/icon picker)
- workspace type (locked after creation in v1; allow change in v2 only)
- role label mapping (P1; default mapping applies per type)

Danger zone:
- Archive workspace (Owner/Admin)
- Delete workspace (Owner)
- Transfer ownership (Owner)

## §5.2.6 Membership & Roles

### §5.2.6.1 Member List Page

Route: `/w/:workspaceId/members` (Viewer+)

Shows:
- member avatar + name + email
- role badge (type-mapped label)
- last active (P2)
- actions (Admin+):
  - change role dropdown
  - remove member
  - resend invite (pending invites view)

### §5.2.6.2 Invitations (Integration with FL-004)

- Members tab includes:
  - “Invite members” button (Admin+)
  - Pending invitations table:
    - email, role, invitedBy, createdAt, expiresAt, status
    - actions: resend, revoke (Admin+)

### §5.2.6.3 Role Change Rules (v1)

- Owner can assign any workspace role
- Admin can assign roles up to Manager (cannot create Admin or Owner)
- Cannot remove or demote the Owner without transferring ownership first
- Changing roles is immediate and must take effect in real-time:
  - user’s next API call should enforce new role
  - open collaboration sessions should lose edit capability if downgraded

## §5.2.7 Workspace Limits & Quotas (v1 defaults)

These are configurable; defaults are chosen for safety in early deployments.

| Limit | Default | Enforced Where |
|------|---------|----------------|
| Max workspaces per user | 20 | API validation on create |
| Max members per workspace | 50 | API validation on invite/accept |
| Max documents per workspace | 500 | API validation on create doc |
| Max tasks per workspace | 2,000 | API validation on create task |
| Max file storage per workspace | 5GB | file upload service (P2) |

When a limit is reached, return a clear error code and message:
- `WORKSPACE_LIMIT_REACHED`
- `WORKSPACE_MEMBER_LIMIT_REACHED`
- etc.

## §5.2.8 API Contracts (Authoritative)

Base: `/api/v1/workspaces`

### 1) List Workspaces
`GET /api/v1/workspaces`

Response (200):
```json
{
  "data": {
    "items": [
      {
        "id": "uuid",
        "name": "Project Alpha",
        "description": "Building X",
        "type": "professional",
        "icon": "📦",
        "myRole": "MANAGER",
        "roleLabel": "Tech Lead",
        "lastAccessedAt": "2025-07-17T12:00:00Z",
        "createdAt": "2025-07-10T12:00:00Z"
      }
    ]
  }
}
```

Notes:
- Include `myRole` and `roleLabel` for UI display.
- `lastAccessedAt` is tracked per user-workspace membership.

### 5) Archive / Unarchive
`POST /api/v1/workspaces/:workspaceId/archive`  
`POST /api/v1/workspaces/:workspaceId/unarchive`

Role: Admin+  
Response (200):
```json
{ "data": { "workspaceId": "uuid", "status": "archived" } }
```

### 6) Delete Workspace (Soft Delete)
`DELETE /api/v1/workspaces/:workspaceId`

Role: Owner  
Behavior:
- soft delete workspace (set `deleted_at`)
- optionally soft delete related entities or rely on workspace scoping + purge job

Response:
```json
{ "data": { "message": "Workspace deleted. It can be restored within 90 days." } }
```

Errors:
- `403 FORBIDDEN`

---

### 8) Members: Change Role
`PATCH /api/v1/workspaces/:workspaceId/members/:membershipId/role`

Role: Admin+ (Owner can set any)  
Request:
```json
{ "role": "MEMBER" }
```

Errors:
- `400 CANNOT_DEMOTE_OWNER`
- `403 FORBIDDEN_ROLE_ASSIGNMENT`
- `404 MEMBER_NOT_FOUND`

---

### 9) Members: Remove
`DELETE /api/v1/workspaces/:workspaceId/members/:membershipId`

Role: Admin+ (Owner can remove any; Admin cannot remove Owner/Admin)  
Errors:
- `400 CANNOT_REMOVE_OWNER`
- `403 FORBIDDEN`

---

### 10) Transfer Ownership
`POST /api/v1/workspaces/:workspaceId/transfer-ownership`

Role: Owner  
Request:
```json
{ "newOwnerUserId": "uuid" }
```

Rules:
- new owner must be an existing member with role Admin or Manager (or elevate during transfer)
- after transfer, previous owner becomes Admin

Errors:
- `400 INVALID_NEW_OWNER`
- `403 FORBIDDEN`

## §5.2.9 Data Model (Authoritative)

### `workspaces`
- `id UUID PK`
- `name VARCHAR(60) NOT NULL`
- `description VARCHAR(280) NULL`
- `type ENUM('professional','academic','general') NOT NULL`
- `icon VARCHAR(16) NULL` (emoji or short code)
- `status ENUM('active','archived') NOT NULL DEFAULT 'active'`
- `owner_id UUID NOT NULL` (FK to users)
- `created_at`, `updated_at`, `deleted_at`

Indexes:
- `(owner_id, created_at DESC)`
- `(deleted_at)` partial index for active workspaces

### `workspace_members`
- `id UUID PK`
- `workspace_id UUID FK`
- `user_id UUID FK`
- `role ENUM('OWNER','ADMIN','MANAGER','MEMBER','VIEWER')`
- `joined_at`
- `left_at NULL`
- `last_accessed_at NULL`
- `is_active BOOLEAN DEFAULT true`

Constraints:
- Unique `(workspace_id, user_id)` where `left_at IS NULL` (or `is_active=true`)
- Exactly one Owner per workspace enforced by application logic (and optionally DB partial unique index on owner role per workspace)

Indexes:
- `(workspace_id, role)`
- `(user_id, last_accessed_at DESC)`

### `workspace_settings`
- `workspace_id UUID PK/FK`
- `settings JSONB NOT NULL`
  - includes feature flags:
    - `submissionWorkflowEnabled` (default true for academic)
    - `allowViewerCommentsOnDocs` (default true)
    - `allowViewerCommentsOnTasks` (default false)
  - includes UI settings:
    - `roleLabels` mapping (Owner/Admin/Manager/Member/Viewer)
- `created_at`, `updated_at`

> v1 implementation can embed role labels in `workspace_settings.settings.roleLabels`.

## §5.2.10 Events & Side Effects

### Events emitted
| Event | When | Payload |
|------|------|---------|
| `workspace.created` | on create | `{ workspaceId, ownerId, type, templateId }` |
| `workspace.updated` | settings updated | `{ workspaceId, actorId, changes }` |
| `workspace.archived` | archived | `{ workspaceId, actorId }` |
| `workspace.unarchived` | unarchived | `{ workspaceId, actorId }` |
| `workspace.deleted` | deleted | `{ workspaceId, actorId }` |
| `workspace.member_invited` | invite created | `{ workspaceId, invitationId, invitedEmail, role }` |
| `workspace.member_joined` | invite accepted | `{ workspaceId, userId, role }` |
| `workspace.member_role_changed` | role updated | `{ workspaceId, userId, fromRole, toRole }` |
| `workspace.member_removed` | removed | `{ workspaceId, userId, removedBy }` |
| `workspace.ownership_transferred` | transfer | `{ workspaceId, fromUserId, toUserId }` |

### Activity feed rules
- Record activity for:
  - workspace created
  - member joined/removed/role changed
  - workspace archived/unarchived
- Do NOT spam activity with minor settings edits (optional; coalesce)

## §5.2.11 Edge Cases (Must Be Handled)

| Scenario | Expected Behavior |
|---------|-------------------|
| User tries to access workspace they are not a member of | `403 NOT_WORKSPACE_MEMBER` + UI redirect to `/workspaces` |
| Workspace deleted | `404 WORKSPACE_NOT_FOUND` on all workspace routes |
| Owner tries to leave workspace | Block with `400 CANNOT_LEAVE_AS_OWNER` and show “Transfer ownership first” |
| Admin tries to remove Owner | Block with `400 CANNOT_REMOVE_OWNER` |
| Role downgrade while user is editing document | Collaboration server rejects updates; client shows “Edit access removed” banner |
| Archived workspace write attempts | API returns `403 WORKSPACE_ARCHIVED_READONLY`; UI shows read-only banner |
| Member limit reached | Invites/acceptance blocked with `WORKSPACE_MEMBER_LIMIT_REACHED` |
| Duplicate membership creation race | Use unique constraint + transactional logic; return idempotent success |

## §5.2.12 Testing Requirements

### Unit
- role assignment rules (max assignable role)
- ownership transfer logic
- archived workspace write guards

### Integration
- create workspace initializes owner membership + settings
- update workspace requires Admin+
- archive toggles status and blocks write endpoints
- member role change propagates to permission checks
- remove member invalidates their access (subsequent requests forbidden)

### E2E (Playwright)
- create workspace wizard → land in workspace
- invite member → accept invite → member appears
- role changes update UI restrictions
- archive workspace → verify edit actions disabled
