# §5 — Feature Specifications

## §5.1 Authentication & Session Management

### §5.1.1 Overview

Authentication and session management enable users to securely access CollabSphere using either:

- **Email + password** (local authentication)
- **Google OAuth** (social login)

Sessions are implemented using:
- **Short-lived JWT access tokens** (15 minutes)
- **Long-lived refresh tokens** (7 days) stored securely and rotated on refresh

This module also provides:
- Email verification
- Password reset
- Logout (single session + all sessions)
- Account deactivation support (Platform Admin)
- Security logging (audit events)

**Priority:** P0 (launch-blocking)

---

### §5.1.2 Personas & Permissions

| Persona | Capabilities |
|--------|--------------|
| Any user | Register, verify email, login, refresh session, logout, reset password |
| Platform Admin | Deactivate/reactivate users, reset user password (admin action) |

**Workspace role is not relevant** for auth endpoints.

### §5.1.4 Account Lifecycle & Status

#### User Account Status (Global)
User accounts can be in one of these states:

| State | Meaning | Allowed Actions |
|------|---------|-----------------|
| `unverified` | Registered but email not verified (local auth) | Can request verification resend; cannot login |
| `active` | Verified and active | Full access |
| `deactivated` | Disabled by Platform Admin | Cannot login; cannot refresh |
| `deleted` | Soft-deleted user | Cannot login; scheduled purge later |

**Implementation note:** Represent status using:
- `users.is_verified` (boolean)
- `users.is_active` (boolean)
- `users.deleted_at` (timestamp nullable)

Mapping:
- `unverified` → `is_verified=false`, `is_active=true`, `deleted_at=null`
- `active` → `is_verified=true`, `is_active=true`, `deleted_at=null`
- `deactivated` → `is_active=false`
- `deleted` → `deleted_at != null`

### §5.1.5 Session Model

#### Tokens (v1)

| Token | Format | TTL | Storage | Purpose |
|------|--------|-----|---------|---------|
| Access Token | JWT | 15 minutes | In memory (frontend) | Authorizes API requests |
| Refresh Token | Opaque random string | 7 days | httpOnly cookie (recommended) | Obtain new access token |

#### JWT Claims (Access Token)

```json
{
  "sub": "user-uuid",
  "email": "user@example.com",
  "globalRole": "USER",
  "iat": 1710000000,
  "exp": 1710000900
}
```

**Notes**
- Do NOT include workspace membership in JWT (membership can change; must be checked per request)
- Include `jti` (token id) optionally for audit/debugging

#### Refresh Token Rotation

- Every refresh request:
  1) validates refresh token
  2) **rotates** it (invalidates old, issues new)
  3) issues new access token

This reduces replay risk.

### §5.1.6 Backend Authentication Strategy

#### Local Auth
- Password hashing:
  - **bcrypt** cost factor 12 (v1)
  - store only `password_hash`
- Email normalization:
  - always lowercase + trim
- Login requires:
  - `is_verified = true`
  - `is_active = true`
  - `deleted_at IS NULL`

#### Google OAuth
- Uses OAuth 2.0 authorization code flow
- Store:
  - `auth_provider = "google"`
  - `auth_provider_id = <google sub>`
- Treat OAuth users as verified (`is_verified = true`)

#### Account Linking (v1)
- **Not supported** automatically.
- If email exists with local auth and user tries Google OAuth:
  - deny with `ACCOUNT_EXISTS_LOCAL`
- If email exists with google auth and user tries local register:
  - deny with `ACCOUNT_EXISTS_OAUTH`

(We can add account linking in v1.1+ as a deliberate feature with explicit verification.)

### §5.1.7 API Contracts (Authoritative)

Base: `/api/v1/auth`

#### 1) Register (Local)
`POST /api/v1/auth/register`

Request:
```json
{
  "fullName": "Jane Doe",
  "email": "jane@example.com",
  "password": "StrongPass@123"
}
```

Response (201):
```json
{
  "data": {
    "message": "Registration successful. Please verify your email."
  }
}
```

Errors:
- `400 VALIDATION_ERROR`
- `409 EMAIL_ALREADY_EXISTS`
- `429 RATE_LIMITED`

Side effects:
- Creates user (unverified)
- Creates verification token (24h)
- Sends verification email

---

#### 2) Resend Verification Email
`POST /api/v1/auth/resend-verification`

Request:
```json
{ "email": "jane@example.com" }
```

Response (200):
```json
{ "data": { "message": "If an account exists, a verification email has been sent." } }
```

Notes:
- Response must be non-enumerating (same response even if user doesn’t exist).

---

#### 3) Verify Email
`POST /api/v1/auth/verify-email`

Request:
```json
{ "token": "opaque-verification-token" }
```

Response (200):
```json
{ "data": { "message": "Email verified successfully." } }
```

Errors:
- `400 TOKEN_INVALID`
- `410 TOKEN_EXPIRED`
- `400 TOKEN_ALREADY_USED`

---

#### 4) Login (Local)
`POST /api/v1/auth/login`

Request:
```json
{
  "email": "jane@example.com",
  "password": "StrongPass@123"
}
```

Response (200):
```json
{
  "data": {
    "accessToken": "jwt...",
    "user": {
      "id": "uuid",
      "email": "jane@example.com",
      "fullName": "Jane Doe",
      "globalRole": "USER",
      "isVerified": true
    }
  }
}
```

Refresh token delivery:
- Set refresh token cookie: `Set-Cookie: refresh_token=...; HttpOnly; Secure; SameSite=Lax`

Errors:
- `400 INVALID_CREDENTIALS`
- `403 EMAIL_NOT_VERIFIED`
- `403 ACCOUNT_DEACTIVATED`

---

#### 5) Refresh Session
`POST /api/v1/auth/refresh`

Request body: none (refresh token from cookie)

Response (200):
```json
{
  "data": {
    "accessToken": "new-jwt..."
  }
}
```

Errors:
- `401 REFRESH_TOKEN_MISSING`
- `401 REFRESH_TOKEN_INVALID`
- `403 ACCOUNT_DEACTIVATED`

Side effects:
- rotate refresh token cookie

---

#### 6) Logout (Current Session)
`POST /api/v1/auth/logout`

Behavior:
- invalidates current refresh token
- clears refresh token cookie

Response (200):
```json
{ "data": { "message": "Logged out." } }
```

---

#### 7) Logout All Sessions
`POST /api/v1/auth/logout-all`

Behavior:
- invalidates all refresh tokens for user
- clears cookie

Response (200):
```json
{ "data": { "message": "Logged out of all sessions." } }
```

---

#### 8) Forgot Password
`POST /api/v1/auth/forgot-password`

Request:
```json
{ "email": "jane@example.com" }
```

Response (200):
```json
{ "data": { "message": "If an account exists, a reset link has been sent." } }
```

Notes:
- Non-enumerating response.

---

#### 9) Reset Password
`POST /api/v1/auth/reset-password`

Request:
```json
{
  "token": "opaque-reset-token",
  "newPassword": "NewStrongPass@123"
}
```

Response (200):
```json
{ "data": { "message": "Password updated successfully." } }
```

Errors:
- `400 TOKEN_INVALID`
- `410 TOKEN_EXPIRED`
- `400 TOKEN_ALREADY_USED`

Side effects:
- invalidates all refresh tokens (force re-login everywhere)

---

### §5.1.8 Data Model (Authoritative)

#### `users`
Key fields:
- `id UUID PK`
- `email VARCHAR(255) UNIQUE` (store normalized lowercase)
- `full_name VARCHAR(200)`
- `password_hash VARCHAR(255) NULL` (null for OAuth users)
- `auth_provider VARCHAR(20)` default `local`
- `auth_provider_id VARCHAR(255) NULL`
- `is_verified BOOLEAN`
- `is_active BOOLEAN`
- `global_role ENUM('USER','ADMIN')`
- `created_at`, `updated_at`, `deleted_at`

#### `refresh_tokens`
Stores refresh tokens hashed.

- `id UUID PK`
- `user_id UUID FK`
- `token_hash CHAR(64)` (sha256)
- `created_at`
- `expires_at`
- `revoked_at NULL`
- `replaced_by_token_id NULL` (for rotation chain)
- `ip_address NULL`
- `user_agent NULL`

Indexes:
- `(user_id, expires_at)`
- `(token_hash)` unique

#### `email_verification_tokens`
- `id UUID PK`
- `user_id UUID FK`
- `token_hash CHAR(64)`
- `expires_at`
- `used_at NULL`
- `created_at`

#### `password_reset_tokens`
- `id UUID PK`
- `user_id UUID FK`
- `token_hash CHAR(64)`
- `expires_at` (30 minutes)
- `used_at NULL`
- `created_at`

### §5.1.9 Security Requirements

#### Rate Limiting (Minimum)
- Register: 5/hour per IP + 5/hour per email
- Login: 10/min per IP
- Forgot password: 5/hour per email + 20/hour per IP
- Verify/reset token endpoints: 30/min per IP
- Refresh: 60/min per user

#### Password Security
- bcrypt cost 12
- Never log passwords
- Don’t leak whether an email exists in forgot-password/resend-verification responses

#### Token Security
- Store only token hashes in DB
- Use `httpOnly` cookies for refresh token
- Access token stored in memory; never in localStorage if possible
- All auth endpoints behind HTTPS only

#### CSRF
- If refresh token is cookie-based, consider CSRF protection:
  - SameSite=Lax + POST-only refresh endpoint is acceptable for v1
  - Add CSRF token protection in v1.1 if needed

#### CORS
- Allow only trusted frontend origins
- Disallow wildcard in production

| Event | When |
|------|------|
| `user.registered` | After successful register |

| `user.email_verified` | After verify |
| `user.login_succeeded` | After login |
| `security.login_failed` | After failed login attempt |

| `user.password_reset_completed` | After reset-password |
| `user.refresh_succeeded` | After refresh |
| `security.refresh_failed` | After invalid refresh |
| `admin.user_deactivated` | Admin disables user |

### §5.1.11 Edge Cases (Must Be Handled)

| Scenario | Expected Behavior |
|---------|-------------------|
| User registers then never verifies | Account remains unverified; allow resend verification; login blocked with `EMAIL_NOT_VERIFIED`. |
| User tries to register with email already used by Google OAuth | Return `409 EMAIL_ALREADY_EXISTS` with message guiding to Google login. |
| User tries Google OAuth with email used by local account | Return error `ACCOUNT_EXISTS_LOCAL` (no silent merge). |
| Refresh token reused after rotation | Detect chain misuse → revoke entire refresh token family (recommended) and force login. |
| User deactivated while session active | Next refresh fails with `ACCOUNT_DEACTIVATED`; access token expires naturally within 15m. |
| Password reset requested for OAuth-only user | Return 200 generic message; do not send reset email OR send email telling to use Google login. |
| User changes email (future) | Must re-verify new email; invalidate sessions (v2). |
| Email provider downtime | Registration still succeeds; resend should retry via worker; UI should show “Unable to send email” messaging. |
