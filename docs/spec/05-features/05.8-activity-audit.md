# §5.8 Activity Feed & Audit Logging (Activity Events vs Security Audit Log)

## §5.8.1 Overview

CollabSphere maintains two distinct logs:

1) **Activity Feed** — user-facing, workspace-scoped timeline of meaningful collaboration events (project progress visibility).  
2) **Audit Log** — admin-facing, security-focused immutable record of sensitive actions (compliance & forensics).

These are not the same system and must be implemented separately to avoid mixing UX noise with security requirements.

**Priority:**
- P0: Workspace activity feed (basic)
- P1: Security audit log (admin-only) + retention controls
- P2: Advanced filtering, exports, analytics, anomaly detection

---

## §5.8.2 Definitions

### §5.8.2.1 Activity Event
A record of “something that happened in a workspace” that is relevant to members for progress and collaboration context.

Examples:
- Task created/assigned/completed
- Document created/renamed/moved/submitted/approved
- Member joined/left
- Comment added/resolved
- Workspace archived/unarchived

### §5.8.2.2 Audit Log Event
A record of “security-sensitive or policy-sensitive actions” used for incident response, compliance, and admin oversight.

Examples:
- Failed login attempts
- Password reset requested/completed
- Role changes (workspace membership permissions)
- Data exports
- Admin user deactivation
- Ownership transfers
- Template changes (future)
- Bulk deletes

Audit log must be:
- Immutable (no edit/delete via UI)
- Accessible only to Platform Admin (and optionally workspace Owner for workspace-scoped audit)

---

## §5.8.3 Personas & Permissions

### Activity Feed
- Visible to: **all workspace members** (Viewer+)
- Sensitive activity events can be hidden from Viewer based on workspace settings (optional P2)

### Audit Log
- Visible to: **Platform Admin** only in v1
- Optional v1.1: Workspace Owner can view workspace-scoped audit log (not global)

### §5.8.4.3 Activity Event Payload (Canonical)

An activity event must include:
- workspaceId
- actorId (nullable for system)
- eventKey
- summary (human-readable)
- resource references (type + id)
- metadata (JSON for UI)
- createdAt

Example payload:
```json
{
  "id": "evt-uuid",
  "workspaceId": "ws-uuid",
  "actor": { "id": "u-uuid", "fullName": "Alice", "avatarUrl": null },
  "eventKey": "task.assigned",
  "summary": "Jane assigned “Implement login” to Bob",
  "resource": {
    "type": "task",
    "id": "task-uuid",
    "title": "Implement login"
  },
  "metadata": {
    "fromAssigneeId": null,
    "toAssigneeId": "bob-uuid"
  },
  "createdAt": "2025-07-17T12:00:00Z"
}
```

---

### §5.8.4.4 Document Edit Activity Coalescing (Important)

Real-time editing creates too many events. We need a coalescing strategy:

**Rule:** create at most one “document edited” activity event per user per document per time window.

Suggested window:
- 5 minutes

Behavior:
- When collaboration session persists state (or on disconnect), emit `document.edited` event with:
  - actorId
  - documentId
  - “Alice edited ‘SRS’”
- If another edit event by same actor for same doc occurs within 5 minutes:
  - update the existing activity event timestamp OR skip creating a new one

**v1 Simplification:**  
Do not log `document.edited` at all; log only document lifecycle events (created, renamed, moved, submitted). This is acceptable if you want to avoid complexity. If you include it, coalesce.

---

### §5.8.4.5 Activity Feed UI Requirements

Activity feed list item shows:
- actor avatar + name
- summary text
- timestamp (relative)
- resource link (click navigates to resource)
- icon based on event type
- “View details” (optional)

Pagination:
- 25/page, with infinite scroll
- must be ordered by `created_at DESC`

Realtime updates:
- New activity events pushed via socket to `workspace:<workspaceId>` room
- If realtime unavailable, poll every 15–30 seconds

Filtering (P1):
- by event type
- by actor
- by date range

## §5.8.5 Audit Logging Specifications (P1)

### §5.8.5.1 Audit Event Types (v1)

| Event Key | Example | Severity |
|----------|---------|----------|
| `security.login_failed` | Invalid password attempt | warn |
| `security.login_succeeded` | Successful login | info |
| `security.oauth_failed` | OAuth state mismatch | error |
| `security.password_reset_requested` | Forgot password requested | info |
| `security.password_reset_completed` | Password changed via reset | info |
| `security.password_changed` | User changed password | info |
| `security.refresh_failed` | Invalid refresh token | warn |
| `admin.user_deactivated` | Admin disabled account | info |
| `admin.user_reactivated` | Admin re-enabled account | info |
| `workspace.role_changed` | Role changed | info |
| `workspace.ownership_transferred` | Owner changed | info |
| `data.export_requested` | Document export triggered | info |
| `data.export_downloaded` | Export downloaded | info |
| `workspace.deleted` | Workspace deleted | info |
| `file.download_url_issued` (v1.1) | Signed URL issued | info |

> Audit log must include IP address and user agent for auth events.

---

### §5.8.5.2 Audit Event Payload (Canonical)

Audit events must include:
- requestId
- actorId (nullable)
- actorEmail (denormalized)
- globalRole
- actionKey
- target type/id (if any)
- workspaceId (optional)
- ipAddress
- userAgent
- createdAt
- severity
- metadata (JSONB)

Example:
```json
{
  "id": "audit-uuid",
  "requestId": "req_abc123",
  "severity": "warn",
  "actionKey": "security.login_failed",
  "actorId": null,
  "actorEmail": "jane@example.com",
  "ipAddress": "203.0.113.10",
  "userAgent": "Mozilla/5.0 ...",
  "metadata": {
    "reason": "INVALID_CREDENTIALS"
  },
  "createdAt": "2025-07-17T12:00:00Z"
}
```

Notes:
- For failed login, `actorId` may be null (user not authenticated), but store email attempted.
- Never store raw passwords or tokens.

---

### §5.8.5.3 Audit Log UI (Admin)

Route: `/admin/audit`

Features:
- Table with filters:
  - actionKey
  - severity
  - date range
  - actor email
  - workspaceId
- Pagination 50/page
- Expand row to see JSON metadata
- Export audit logs (CSV) (P2; admin-only)

---

### §5.8.5.4 Immutability & Retention

Audit logs must be append-only:
- No API endpoint for edit/delete
- DB-level protection (optional):
  - separate DB role without delete permission
  - or write-only append pattern
- Retention:
  - v1 default: 365 days
  - configurable
- Storage size:
  - consider partitioning by month (P2) if volume grows

- `page`, `pageSize`

## §5.8.7 Data Model (Authoritative)

### `activity_events`
- `id UUID PK`
- `workspace_id UUID FK`
- `actor_id UUID NULL`
- `event_key VARCHAR(80)`
- `summary VARCHAR(255)`
- `resource_type VARCHAR(40) NULL`
- `resource_id UUID NULL`
- `metadata JSONB`
- `created_at TIMESTAMPTZ`

Indexes:
- `(workspace_id, created_at DESC)`
- `(workspace_id, event_key, created_at DESC)`
- `(workspace_id, actor_id, created_at DESC)` (optional)

---

### `audit_log`
- `id UUID PK`
- `request_id VARCHAR(64)`
- `severity ENUM('info','warn','error')`
- `action_key VARCHAR(120)`
- `actor_id UUID NULL`
- `actor_email VARCHAR(255) NULL`
- `actor_global_role ENUM('USER','ADMIN') NULL`
- `workspace_id UUID NULL`
- `target_type VARCHAR(40) NULL`
- `target_id UUID NULL`
- `ip_address VARCHAR(64) NULL`
- `user_agent TEXT NULL`
- `metadata JSONB`
- `created_at TIMESTAMPTZ`

Indexes:
- `(created_at DESC)`
- `(action_key, created_at DESC)`
- `(actor_email, created_at DESC)`
- `(workspace_id, created_at DESC)`

---

## §5.8.8 Events (Internal)

Activity and audit records should be produced via event listeners.

Example:
- `task.assigned` domain event triggers:
  - ActivityEventService → insert `activity_events`
  - NotificationService → insert `notifications` + push realtime
  - AuditLogService → insert `audit_log` (optional; assignment is permission-sensitive so it can be audit-worthy)

## §5.8.9 Edge Cases

| Scenario | Expected Behavior |
|---------|-------------------|
| High activity volume | Pagination + indexes required; consider retention (e.g., 180 days) for activity events. |
| Activity spam from realtime edits | Coalesce or skip document edit events (see §5.8.4.4). |
| Member removed from workspace | Past activity events remain; actor names shown even if user removed (display "Former member" badge). |
| User deleted | Activity retains author as “Deleted user” with cached display name. Audit log retains actor_email. |
| Cross-workspace leakage | Activity queries always filter by workspaceId and membership. Audit queries admin-only. |

## §5.8.10 Observability

Metrics:
- `activity_events.created.count` (by event_key)
- `audit_log.created.count` (by action_key, severity)

- `activity_event_insert_failed` (error)
- `audit_log_insert_failed` (critical error; must not crash request)
