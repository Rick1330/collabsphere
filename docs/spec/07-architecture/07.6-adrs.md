## §7.6 Architecture Decision Records (ADRs)

### ADR-001 — Modular Monolith over Microservices

- **Status:** Accepted
- **Context:** v1 team size is small; product scope is broad (auth, docs, tasks, realtime).
- **Decision:** Use a modular monolith (NestJS modules) with a single Postgres database.
- **Rationale:**
  - Lower operational overhead
  - Faster iteration
  - Easier debugging
  - Strong internal boundaries still possible
- **Consequences:**
  - Single deploy unit for API (simpler)
  - Must enforce module boundaries via code structure and review
- **Alternatives considered:**
  - Microservices: rejected due to ops complexity (service mesh, distributed tracing, data ownership)

---

### ADR-002 — PostgreSQL as Primary Database

- **Status:** Accepted
- **Decision:** Use PostgreSQL 16 for structured storage + full-text search (FTS).
- **Rationale:**
  - Relational data model fits workspaces/members/docs/tasks
  - ACID transactions help enforce workspace isolation
  - PostgreSQL FTS sufficient for v1
  - JSONB available for flexible fields (anchors, metadata)
- **Alternatives considered:**
  - MongoDB: rejected (relational model + constraints + joins needed)
  - Elasticsearch as primary search: rejected (v1 overkill)

---

### ADR-003 — Prisma as ORM

- **Status:** Accepted
- **Decision:** Use Prisma for schema, migrations, and typed queries.
- **Rationale:**
  - Excellent TypeScript type generation
  - Good developer ergonomics for contributors
  - Migration workflow is clear and safe
- **Alternatives considered:**
  - TypeORM: acceptable, but Prisma chosen for stronger typing and modern DX

---

### ADR-004 — Temporary Static Web Placeholder for the PRJ-01 Deployment Stage

- **Status:** Superseded by ADR-012
- **Decision:** Keep the `apps/web` surface as a minimal static placeholder that builds into `apps/web/dist` during the PRJ-01 deploy/bootstrap stage.
- **Rationale:**
  - This matched the current repo implementation and deployment surface during the earlier staging recovery and Vercel bootstrap work.
  - The local/dev/build tooling staged `index.html` rather than a framework-specific server runtime, so the placeholder kept present-state docs truthful.
  - It avoided pretending the long-term product frontend already existed before PRJ-02 was ready to establish it.
- **Consequences:**
  - This decision described temporary implementation truth, not the intended final product frontend architecture.
  - PRJ-02 must replace the placeholder through an explicit web-platform transition baton instead of treating the placeholder as final architecture.
- **Alternatives considered:**
  - Claim Next.js App Router was already implemented: rejected because it was false during PRJ-01.
  - Leave the web surface undocumented: rejected because deploy and local runtime truth still had to be explicit.

### ADR-005 — Tiptap + Yjs for Collaborative Editing

- **Status:** Accepted
- **Decision:** Use Tiptap for editor and Yjs for CRDT.
- **Rationale:**
  - Battle-tested CRDT library (do not build CRDT ourselves)
  - Tiptap integrates cleanly with Yjs
  - Supports awareness (presence/cursors)
- **Alternatives considered:**
  - Build CRDT from scratch: rejected (high risk, long timeline)
  - OT (Operational Transform): rejected for v1 complexity; CRDT stack chosen

---

### ADR-006 — Hocuspocus as Collaboration Server

- **Status:** Accepted
- **Decision:** Use Hocuspocus for WebSocket sync + persistence hooks.
- **Rationale:**
  - Official Tiptap collaboration backend
  - Provides extension hooks for auth and storage
  - Scaling support via Redis
- **Consequences:**
  - Requires a dedicated service (apps/collab)
  - Requires persistence strategy (store Yjs state in Postgres)
- **Alternatives considered:**
  - y-websocket server: acceptable; Hocuspocus chosen for better hooks/ops

---

### ADR-007 — Socket.IO for App Realtime Events

- **Status:** Accepted
- **Decision:** Use Socket.IO for non-editor realtime events (notifications, tasks, activity).
- **Rationale:**
  - Room model fits workspace/user scoping
  - Reconnect handling and fallbacks built-in
- **Alternatives considered:**
  - SSE: acceptable for one-way updates, but Socket.IO provides bidirectional UX hooks
  - Raw WebSocket: more work, less DX

---

### ADR-008 — Event-Driven Internal Side Effects

- **Status:** Accepted
- **Decision:** Use an internal event bus pattern so domain services emit events and side effects are handled by listeners.
- **Rationale:**
  - Avoid tight coupling (TaskService doesn’t call NotificationService directly)
  - Makes future integrations (webhooks/Slack/GitHub) additive
- **Alternatives considered:**
  - Direct service-to-service calls: rejected (harder to extend cleanly)

---

### ADR-009 — S3-Compatible Storage for Files

- **Status:** Accepted (v1.1)
- **Decision:** Use S3-compatible object storage with presigned URLs.
- **Rationale:**
  - Scales better than DB blobs
  - Works with AWS S3 and MinIO locally
- **Alternatives considered:**
  - Store files in DB: rejected (performance/size)

---

### ADR-010 — BullMQ for Background Jobs

- **Status:** Accepted
- **Decision:** Use BullMQ (Redis-backed) for email, export, cleanup.
- **Rationale:**
  - Reliable retries and scheduling
  - Good Node ecosystem support
- **Alternatives considered:**
  - Cron-only jobs: rejected (needs retries, queue visibility)

### ADR-011 — Vercel + Azure Container Apps Deployment Target

- **Status:** Accepted
- **Decision:** Deploy `web` on Vercel, and deploy `api`, `collab`, and `worker` as OCI-compatible containers on Azure Container Apps.
- **Rationale:**
  - The current `web` surface is a Next.js App Router application that aligns with Vercel.
  - The backend requires long-lived containerized services, health checks, and shared runtime configuration across `api`, `collab`, and `worker`.
  - Azure Container Apps provides a managed container runtime without forcing a platform-specific rewrite of the backend services.
  - Retaining OCI-compatible container packaging keeps DigitalOcean and other standard container hosts viable as fallbacks.
- **Consequences:**
  - CS-008 deployment work must target Azure Container Apps instead of Railway.
  - Deployment validation must prove the Vercel frontend and Azure Container Apps backend path rather than a Railway path.
  - Object-storage provider selection remains separate from the runtime decision; Cloudflare R2 may be evaluated later without changing the immediate deployment target.
- **Alternatives considered:**
  - Railway: rejected as the active CS-008 backend target after the architecture correction.
  - Cloudflare Workers as the primary backend runtime: rejected because the current backend is built as containerized Node services rather than an edge-function runtime.
  - DigitalOcean as the primary host: acceptable fallback, but not the preferred managed runtime for the corrected v1 deployment plan.

### ADR-012 — PRJ-02 Web Frontend Foundation on Next.js App Router

- **Status:** Accepted
- **Decision:** `apps/web` uses Next.js App Router on Vercel as the implemented frontend foundation for PRJ-02. The former static placeholder surface has been retired.
- **Rationale:**
  - PRJ-02 story contracts require a real application frontend with nested layouts, authenticated app shell behavior, theme/state providers, responsive navigation, page-state composition, and richer route handling than the former placeholder could honestly provide.
  - Vercel remains the correct deployment target; the mismatch is the frontend surface, not the host.
  - Landing the App Router foundation unblocks truthful implementation of downstream PRJ-02 stories without forcing feature-complete UI into the platform-transition baton.
- **Consequences:**
  - Canonical docs, AGENTS files, and deployment references must now describe the Next.js foundation as current truth.
  - Vercel deploy workflow steps must execute from `apps/web` rather than staging a fake static `apps/web/dist` artifact.
  - PRJ-02 feature stories remain separate implementation work; the platform transition does not count as story completion.
- **Alternatives considered:**
  - Keep the placeholder static surface as the intended final frontend: rejected because it cannot satisfy the PRJ-02 application-shell story contracts.
  - Move the frontend away from Vercel: rejected because deployment target is not the actual architecture problem.
  - Leave the frontend framework unspecified: rejected because PRJ-02 sequencing needs an explicit implemented platform foundation.
