## §6.4 Availability & Reliability Requirements

### NFR-R01 — Availability Target

**Target**
- v1 target uptime: **99.5%** monthly

Allowed downtime:
- ~3.6 hours/month

---

### NFR-R02 — Graceful Degradation

If a dependency fails, the system should degrade gracefully:

| Dependency Failure | Expected Behavior |
|-------------------|------------------|
| Email provider down | In-app notifications still work; email jobs queued and retried |
| Redis down | Rate limiting may degrade; realtime may degrade; core REST operations must still work |
| Collaboration server down | Documents open read-only with banner “Collaboration offline”; retry reconnect; content preserved |
| Storage provider down | File uploads disabled; downloads may fail; core tasks/docs still work |
| Search index stale | Search returns partial results; show “results may be incomplete” (optional) |

---

### NFR-R03 — Backups & Recovery

**Database**
- Automated backups every 24 hours minimum
- Point-in-time recovery (PITR) recommended if using managed DB
- Restore point target: **< 24 hours data loss** max (v1)

**Files**
- Stored in object storage with provider durability guarantees
- If self-hosting MinIO, backup policies must be defined (v1.1)

---

### NFR-R04 — Offline Editing (Collaboration)

**Requirement**
- If a user’s connection drops temporarily, the editor must not lose local changes.
- Yjs offline queue + merge ensures this.

**Expected UX**
- Banner: “Offline — changes will sync when reconnected”
- On reconnect: banner clears and “Synced” appears
