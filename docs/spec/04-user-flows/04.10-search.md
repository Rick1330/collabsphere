# §4.10 FL-009 — Search (Workspace-Scoped + Global)

## §4.10.1 Goal

Allow users to quickly find content across:
- Documents (titles + indexed text)
- Tasks (titles + descriptions)
- Comments (optional v1.1; v1 can start with documents+tasks)

Search must be:
- Fast (<500ms typical query)
- Permission-safe (no leaks across workspaces or roles)
- Useful (ranked results, highlighted snippets)
- Available via:
  - search bar
  - command palette (Cmd+K)

---

## §4.10.2 Actors

- **Primary:** Any authenticated user
- **Secondary:** System (Search indexer, DB full-text search, ranking)
- **Optional:** Platform admin (global search across all workspaces in admin context)

---

## §4.10.3 Preconditions

- User is authenticated
- User is a member of at least one workspace (for workspace search)
- Content exists (documents/tasks)
- Search indexes exist in DB (PostgreSQL full-text indexes)

---

## §4.10.4 Postconditions (Success)

- User sees categorized results:
  - Documents
  - Tasks
  - (optional) Comments
- Clicking a result navigates directly to its resource:
  - document editor
  - task detail
- Search respects workspace scoping and RBAC
- Results include:
  - title
  - short snippet with highlights
  - workspace name (for global search)
  - last updated time

---

## §4.10.5 Search Modes

### A) Workspace-Scoped Search (default when inside workspace)
- Scope: only current workspace
- Triggered from:
  - top search bar when on `/w/:workspaceId/*`
  - command palette default scope

### B) Global Search (across all user’s workspaces)
- Scope: all workspaces where the user is a member
- Triggered from:
  - top search bar when on global routes
  - toggle in search UI (“All workspaces”)
  - command palette when query prefixed by `@all` (optional)

### C) Admin Global Search (platform admin only)
- Scope: all workspaces and users (admin context)
- Available only under `/admin/*`
- Must be separated from normal user experience to avoid accidental data exposure

---

## §4.10.6 Result Types (v1)

### Documents
- Search fields:
  - `documents.title` (high weight)
  - `documents.plaintext` (derived from CRDT state; medium weight)
- Result fields shown:
  - Title
  - Snippet (plaintext excerpt)
  - Workspace name (global search)
  - Last updated time
  - “Open” action

### Tasks
- Search fields:
  - `tasks.title` (high weight)
  - `tasks.description` (medium weight)
  - Labels (low weight; P2)
- Result fields shown:
  - Title
  - Status badge
  - Assignee
  - Workspace name (global search)
  - Due date (optional)

### Comments
- v1.1:
  - Search comment content
  - Result links directly to thread

## §4.10.7 Data Indexing Strategy (v1)

Because documents are CRDT-based (Yjs), their content is stored as binary updates. We need a **searchable plaintext representation**.

### Required approach
- Store an additional derived column:
  - `documents.content_plaintext` (TEXT)
- Update it:
  - periodically by background job (recommended)
  - or on collaboration persistence hook (if feasible)
- Use this plaintext field for full-text search

### Why not decode on every search?
Decoding CRDT state on-the-fly is expensive and would slow down search. Precomputing plaintext is the correct approach.

## §4.10.8 PostgreSQL Full-Text Search (FTS)

### Document search index
- Create a tsvector index:

```sql
ALTER TABLE documents
ADD COLUMN search_vector tsvector;

UPDATE documents
SET search_vector =
  setweight(to_tsvector('english', coalesce(title,'')), 'A') ||
  setweight(to_tsvector('english', coalesce(content_plaintext,'')), 'B');

CREATE INDEX idx_documents_search_vector
ON documents
USING GIN (search_vector);
```

### Task search index

```sql
ALTER TABLE tasks
ADD COLUMN search_vector tsvector;

UPDATE tasks
SET search_vector =
  setweight(to_tsvector('english', coalesce(title,'')), 'A') ||
  setweight(to_tsvector('english', coalesce(description,'')), 'B');

CREATE INDEX idx_tasks_search_vector
ON tasks
USING GIN (search_vector);
```

### Query strategy
- Use `plainto_tsquery` for basic keyword search
- Use `websearch_to_tsquery` (preferred) for user-friendly search syntax (quoted phrases, etc.)

## §4.10.9 Ranking Rules (v1)

### Scoring
- Documents:
  - Title matches weighted highest
  - Content matches weighted medium
  - Recent updates slightly boosted (P2)
- Tasks:
  - Title matches weighted highest
  - Description matches medium
  - Status not used for score (but may influence display)

### Result grouping
Return grouped results:
- Documents first
- Tasks second
(or mix by score if you prefer; grouping is more readable)

## §4.10.10 UI/UX — Search Bar

### Global search bar behavior
- Input in top nav
- Debounced input (200ms)
- Dropdown results show as user types
- Press Enter:
  - navigates to full search results page:
    - global: `/search?q=...`
    - workspace: `/w/:workspaceId/search?q=...` (optional)
- Dropdown results show max 5 per type, with “View all results” link

### Dropdown result row
- Icon by type
- Title in bold
- Snippet with highlights
- Workspace pill (for global results)
- Keyboard navigation with arrow keys + enter

## §4.10.12 API Contracts (Flow-Level Summary)

### `GET /api/v1/search`

Query params:
- `q` (required)
- `scope=global|workspace`
- `workspaceId` (required if scope=workspace)
- `types=documents,tasks` (optional)
- `page`, `pageSize`

Example:
`GET /api/v1/search?q=login+page&scope=workspace&workspaceId=uuid&types=documents,tasks&page=1&pageSize=25`

Response (200):
```json
{
  "data": {
    "query": "login page",
    "scope": "workspace",
    "workspaceId": "uuid",
    "results": {
      "documents": [
        {
          "id": "doc-uuid",
          "title": "Authentication Requirements",
          "snippet": "…users must be able to <mark>login</mark> using email/password…",
          "updatedAt": "2025-07-17T12:10:00Z",
          "url": "/w/uuid/documents/doc-uuid"
        }
      ],
      "tasks": [
        {
          "id": "task-uuid",
          "title": "Implement login page",
          "snippet": "Build the <mark>login</mark> UI and connect auth endpoints…",
          "status": "in_progress",
          "priority": "high",
          "dueDate": "2025-08-01",
          "url": "/w/uuid/tasks/task-uuid"
        }
      ]
    }
  },
  "meta": {
    "pagination": { "page": 1, "pageSize": 25, "totalItems": 7, "totalPages": 1 }
  }
}
```

Errors:
- `400 VALIDATION_ERROR` (missing q)
- `403 FORBIDDEN` (workspace not accessible)
- `404 WORKSPACE_NOT_FOUND`

## §4.10.13 Security & RBAC Rules

Search must NEVER leak data.

Rules:
1. Workspace search:
   - Must validate membership in that workspace
2. Global search:
   - Must join against `workspace_members` to limit workspaces to those the user belongs to
3. Viewer vs Member:
   - Viewer can search documents/tasks they can view
   - If you later add per-document visibility, search must respect it too
4. Admin search:
   - Only on admin routes with admin guard
   - Not membership-scoped; scope is all workspaces/users in admin context (exclude soft-deleted entities)

## §4.10.14 Events Emitted

Search does not emit activity events by default (to avoid noise). However, we record analytics events (optional) for UX improvement:

| Event | Trigger | Payload |
|-------|---------|---------|
| `search.performed` | search endpoint called | `{ userId, scope, queryLength, types }` |
| `search.result_clicked` | user clicks result | `{ userId, type, resourceId }` |

## §4.10.15 Edge Cases

| Edge Case | Expected Behavior |
|----------|-------------------|
| Empty query | UI disables submit; API returns 400. |
| Query with special characters | Use `websearch_to_tsquery` to handle safely. |
| Very long query (>200 chars) | Truncate client-side and return 400 if exceeded. |
| User searches globally but belongs to many workspaces | Paginate and limit results per workspace to avoid bias (P2). |
| Search index stale for CRDT docs | Acceptable if plaintext updates lag slightly. Provide “Last indexed X minutes ago” (optional). |
| Non-English text | Use `'simple'` dictionary or configurable per workspace language (v2). |
| Performance degradation | Add indexes, limit results, and add query timeout warnings in logs. |

## §4.10.16 Observability

Metrics:
- `search.query.count`
- `search.query.latency_ms` (p50/p95/p99)
- `search.query.error.count`
- `search.query.db_time_ms`
- `search.query.result_count` (histogram)

Logs:
- `search_performed` (info): userId, scope, qHash (not raw query), resultCount, latencyMs
- `search_slow_query` (warn): latencyMs, workspaceId
- `search_forbidden` (warn): userId, workspaceId

Privacy note:
- Do not log raw queries in plaintext in production logs; log a hash to avoid leaking sensitive terms.
